1. Introduction 
1.1 Purpose 
This Software Requirements Specification (SRS) defines the scope, tasks, responsibilities, dependencies, and integration  requirements for Milestone 1 of the SwipeX platform. It translates the project charter into a coordinated, day-wise  execution plan for five interns working in parallel, each owning a distinct technical domain, so that their individual  deliverables converge into a single, functioning system increment by the end of Day 7. 
1.2 Scope of Milestone 1 
Milestone 1 covers project initialization, system architecture, and core setup. By the end of Day 7 the team must deliver  a working increment consisting of: an initialized multi-service repository with an agreed architecture; a functioning  authentication and role-based access control (RBAC) system supporting Job Seeker, Recruiter, and Admin roles; a  job/company data schema with a live Job & Swipe Service; a resume-upload flow backed by a heuristic ATS-scoring and  recommendation stub that unblocks downstream integration ahead of real NLP/ML model training in Milestone 2; a  connected frontend exposing login, swipe-based job discovery, and a dashboard shell; and a validated, tested integration  of all of the above inside a local/dev Docker Compose environment. Production deployment is explicitly out of scope for  Milestone 1 and is deferred until all four milestones are complete.

3. Overall Description 
SwipeX is a centralized platform that helps job seekers discover and apply for relevant jobs through an intuitive swipe based interface, backed by AI-powered resume analysis, ATS scoring, personalized recommendations, and real-time  opportunity tracking across MNCs, startups, and newly founded companies. The architecture follows five layers:  Frontend, API Gateway, Backend Services (Job, Swipe, Matching, Resume, ATS Scoring, AI Recommendation, Application,  Notification, Analytics), AI/NLP Services, and the Database & Storage layer (PostgreSQL, Redis, file storage, vector  database), sitting on top of a containerized infrastructure. Milestone 1 establishes the foundation of this stack — the  entry points, the data backbone, and the first three backend services (Authentication, Job/Swipe, and a heuristic  Resume/ATS/Recommendation stub) — while stubbing the deeper AI logic so all layers can be integrated end-to-end  without waiting for full model development.

7. Interface Contracts & Integration Points 
These contracts are frozen by Day 2 so that all five interns can build against a stable interface instead of waiting on one  another's implementation. 
7.1 Authentication & User Service (owner: Intern 1) 
● POST /api/v1/auth/register — { name, email, password, role } → 201 { user_id } 
● POST /api/v1/auth/login — { email, password } → 200 { access_token, refresh_token, role } ● GET /api/v1/auth/oauth/google — OAuth2 login → 200 { access_token, role } 
● POST /api/v1/auth/refresh — { refresh_token } → 200 { access_token } 
● GET /api/v1/auth/me — Header: Bearer token → 200 { user_id, name, role } 
Consumed by: Intern 4 (login UI), Intern 5 (auth test suite), and indirectly by Intern 2 & 3 endpoints that require role-gated  access. 
7.2 Job & Swipe Service (owner: Intern 2) 
● GET /api/v1/jobs?type=&location=&remote=&salary_min=&salary_max=&skills= → 200 [ { job_id, title,  company, type, location, salary_range, skills[], posted_at } ] 
● GET /api/v1/jobs/{job_id} → 200 job detail 
● POST /api/v1/swipes — { job_id, direction } → 201 { swipe_id } 
● GET /api/v1/swipes/history → 200 [ { job_id, direction, swiped_at } ] 
Consumed by: Intern 4 (swipe UI / dashboard), Intern 3 (feature input for the recommendation stub), Intern 5 (functional  + regression tests). 
7.3 Resume & Career Intelligence Service — Heuristic Stub (owner: Intern 3) ● POST /api/v1/resume/upload (multipart file) → 201 { resume_id, parsed_skills[] } 
● GET /api/v1/resume/{resume_id}/ats-score?job_id={id} → 200 { match_score, missing_keywords[],  generated_by: "heuristic-v0" } 
● GET /api/v1/recommendations?user_id={id} → 200 [ { job_id, match_percentage, generated_by: "heuristic-v0"  } ] 
These endpoints use simple rule-based logic (keyword/skill overlap) rather than a trained model. They exist solely to give  Intern 1 (gateway routing), Intern 4 (UI hook-up), and Intern 5 (test coverage) a stable contract to integrate against before  real NLP/embedding-model training begins in Milestone 2.
7.4 Local Integration Environment (owner: Intern 5) 
● docker-compose.dev.yml — brings up PostgreSQL, Redis, and all three backend services together for local  integration testing 
● Shared Postman/pytest collection — used by all interns to validate their endpoints against the frozen contracts  above 
This environment is for local/dev integration validation only and is explicitly not a deployment target. 8. Cross-Team Dependency Matrix

13. Milestone 1 Acceptance Criteria 
● Project initialization, architecture, and database schema are complete and documented. ● Authentication and role-based access control (Job Seeker / Recruiter / Admin) are implemented and enforced  across protected routes.
● Job/company/startup data schema and a live Job & Swipe Service (listing, filter/search, swipe recording) are  functional and expose data via REST APIs. 
● The frontend presents a working login flow, a swipe-based job-discovery interface, and a dashboard shell driven  by real backend data. 
● The Resume Service and heuristic ATS-score/recommendation stub are reachable end-to-end through the  Gateway and displayed on the dashboard, clearly scoped as a placeholder for Milestone 2's trained model. ● All services run together and pass integration/smoke tests inside the local Docker Compose environment. ● CI enforces lint, build, and automated test checks on every pull request. 
● Every tool used across the milestone was free/open-source — no paid subscriptions were required. ● No production deployment activity has occurred; deployment remains explicitly scheduled for after Milestone 4.
